**Executive Verdict**

Yes, the CDE documents satisfy the *shape* of my directive. They correctly reframe Architecture 5 as a measurement-governed ensemble, and they identify the right three variables: candidate quality, error decorrelation, and selector reliability.

But they are not implementation-ready. The largest remaining flaw is that the documents still treat **oracle coverage and complementarity metrics as sufficient evidence**, when the real CDE claim must be:

> Under equal compute, a deployable selector chooses a better answer from a decorrelated operator mix than from the best single operator.

Right now, the design can still “win” on oracle/Jaccard and lose as a usable inference system.

**1. Does CDE Satisfy The Directive?**

Mostly yes.

It includes the required pieces: operator portfolio, diversity metrics, selector audit, N curves, equal-budget comparison, and relationship to the existing temperature experiment. That is the correct architectural direction.

What is still missing:

- A clean separation between **evaluation oracle** and **deployable selector**.
- A candidate-set-level schema. Selection happens over a set, but the trace schema is mostly per-candidate.
- A statistically valid validation plan. `25` arithmetic tasks is a pilot, not a decision-grade experiment.
- A primary endpoint based on **selected accuracy**, not oracle accuracy.
- A stronger equal-budget contract: equal `N`, equal generated-token budget, and equal wall-clock/cost-normalized comparisons.
- A real allocator protocol. The current greedy formula using `A * (1 - rho)` is a heuristic, not a defensible estimator of marginal coverage.
- A held-out split. The same traces are being used for characterization, operator choice, selector tuning, and success claims.

So: correct architecture, incomplete contract.

**2. Measurement Contract And Trace Schema**

The measurement contract is directionally good but incomplete.

Add these metrics:

- **Selected accuracy**: primary system metric.
- **Cost-normalized lift** over best single operator and best temperature/nucleus baseline.
- **Marginal unique solves** per operator: tasks solved by `O_b` that `O_a` misses.
- **Duplicate-basin rate / fingerprint collision rate**.
- **Answer-cluster diversity**: unique normalized answers, answer entropy, answer-cluster oracle.
- **Selector calibration**: precision, recall when oracle-positive, false-positive confidence, ECE/Brier if confidence is used.
- **Oracle-selector gap by N**.
- **Bootstrap or paired permutation CIs over tasks**, not only subset bootstraps over candidates.
- **Cluster-correctness association**: cluster purity or mutual information between trajectory cluster and correctness.
- **Extraction failure / ambiguity rate**: disagreement between answer-anywhere, last integer, final answer, and normalized extracted answer.

De-emphasize or demote:

- `answer_anywhere_correct` as a primary metric. It can over-credit outputs whose final answer is wrong.
- Raw `first_32_embedding` in JSONL as mandatory storage. Store a hash/path/reference or reduced vector; full embeddings can be artifact files.
- DBSCAN `eps=0.3` as a fixed truth. Treat clustering as an analysis method with sensitivity checks.
- Length heuristic as a selector. It is a weak prefilter, not a meaningful selector.

Trace schema is not sufficient yet. Add:

- `run_id`, `candidate_set_id`, `allocation_id`, `panel_id`, `candidate_index`.
- Model identity: checkpoint, quantization, tokenizer hash, chat template, git commit, library versions.
- Full generation config: max tokens, stop condition, top-k, top-p, temperature, repetition penalty, seed state.
- Full prompt/rendered input, not just task text.
- Output token IDs and final-answer extraction method/version.
- Operator artifact hashes: prefix tensor hash/norm/RMS, random token IDs, prompt template text/hash, position offset.
- Evaluator/verifier version and whether the verifier is deployable or oracle-only.
- A separate **selection trace**: selector id, scores/ranks for all candidates, selected trace id, confidence, fallback/abstention decision.

Selectors are set-level objects. They should not be embedded only as per-candidate fields.

**3. Decision Gates And Thresholds**

Several gates need correction.

Gate 1 currently says:

> IF max J < 0.8 for any pair: YES

That is logically wrong. It should be based on **minimum pairwise Jaccard**, not max.

Better gate:

- Candidate pair is complementary only if:
  - both operators are viable: `A >= floor`, `Y >= floor`;
  - `J(correct_sets) <= 0.7` or meaningful unique-solves count;
  - cross-operator error correlation is lower than within-operator correlation;
  - the pair improves oracle and selected accuracy under equal compute.

Threshold changes:

- `A > 0.2` is too absolute. Use relative viability too: operator accuracy should be at least `50-70%` of the best cheap operator unless it contributes unique solves.
- `Y > 0.7` is acceptable as a pilot cutoff, but core Tier 1 operators should probably target `Y > 0.85`.
- `rho < 0.3` is useful as a label, not a hard gate. With only 25 tasks, binary correlations are noisy. Require CIs or relative reduction versus within-operator correlation.
- `+2 tasks on 25` is acceptable as a pilot signal, not a validation claim. For validation, require a held-out larger set and paired uncertainty.
- `selector_accuracy > 60% of oracle` is too weak for arithmetic. For arithmetic/logic, target `>= 80%` of oracle. For legal/open-ended, require judge audit and calibration.

Most important gate change:

> CDE succeeds only if **selected accuracy** beats the best single-operator baseline under equal compute. Oracle improvement alone is not enough.

**4. Operator Portfolio Tiering**

Mostly correct, but change the tiers.

Move to Tier 1:

- **Random Token Prefix**. My prior directive explicitly required prefix vs temperature vs prompt paraphrase vs random-token prefix. It is a required control, not an extended operator.
- **Position Shift**, or at least a Tier 1 control. Zero soft prefix partially tests prefix-position effects, but pure position shift is the cleaner control.

Change treatment:

- **Zero Soft Prefix** is deterministic if decoding is greedy. Do not generate `N=10` identical zero-prefix candidates. Treat it as a control, not a sampled operator.
- **Prompt Rephrase** uses templates, not seeds. Model it as `template_id`, not stochastic seed.
- **Neuro-symbolic** should be in a tool/verifier-augmented track. It is valuable, but it is not a fair black-box candidate generator unless clearly budgeted and domain-scoped.
- **ALM** should be split:
  - basin/cluster measurement belongs in Phase 1 analysis;
  - ALM-guided generation can be Tier 2 after basin stability is proven.
- **CIR, Attention Surgery, GGIO** are correctly Tier 3.

**5. Selector Protocol**

Partly sound, but the missing selector is critical:

> **Operator-stratified answer consensus with abstention.**

Raw majority vote is wrong for CDE because it is biased by allocation. If you sample 6 prefix and 4 rephrase candidates, majority vote mostly measures sampling ratio. The selector should score normalized answer clusters by:

- number of distinct operators supporting the answer;
- per-operator quality prior;
- independence/decorrelation prior;
- within-answer confidence;
- verifier result if available;
- fallback/abstention if no cluster is credible.

Order changes:

For arithmetic/logic/code:

1. Degenerate filter.
2. Normalize/extract candidate answers.
3. Deployable formal verifier if available.
4. Operator-stratified answer-cluster consensus.
5. Self-certainty as tiebreaker, not primary selector.
6. Fallback to greedy/baseline or abstain if confidence is low.

For legal/open-ended:

1. Degenerate filter.
2. Constraint/rubric extraction.
3. LLM judge or pairwise judge over candidates.
4. Cross-operator agreement and confidence calibration.
5. Abstention/fallback path.

Also: exact match against ground truth is not a deployable selector. It is evaluation oracle machinery.

**6. N-Scaling Curves And Subsampling**

Subsampling from `N=10` is valid only for a narrow claim:

> It estimates expected oracle/selected accuracy for subsets of an already generated finite candidate pool, for `N <= 10`.

It is not valid for true `N=16` scaling.

Risks:

- You cannot infer `N=16` from `N=10`; “use all 10 and bootstrap” is invalid for additional unique candidates.
- Candidate subsets are correlated, so CIs will be too optimistic if task-level uncertainty is ignored.
- The `25` task set dominates uncertainty.
- If the same data chooses the operator and estimates the curve, curves are selection-biased.
- Selector behavior changes with N, especially majority vote.
- Finite seed pools can make curves look saturated or unusually strong by accident.

Fix:

- Generate at least `N=16`, preferably `N=30`, for Tier 1 operators if N-scaling is part of the claim.
- Bootstrap over tasks as the primary uncertainty unit.
- Use held-out seed panels for confirmation.
- For top ensembles, generate actual ensemble allocations at target N, not just post-hoc mixtures unless allocation was pre-registered.

**7. Relationship To Temperature Comparison**

The relationship makes sense.

The temperature comparison design should become CDE Experiment 0, not a separate line of work. But it must be upgraded with:

- trace schema;
- random-token prefix Tier 1 control;
- first-32-token fingerprints;
- pairwise error correlation;
- correct-set Jaccard;
- selector audit;
- selected accuracy;
- equal compute and equal token accounting.

Without those additions, it remains only a baseline comparison, not CDE evidence.

**8. Success Criteria**

Section 10 is too oracle-heavy and too weak statistically.

Replace Minimum Viable CDE with:

1. Complete trace and selection records for all Tier 1 operators.
2. At least two viable operators with measurable unique-solves or lower cross-error correlation.
3. Best 2-operator ensemble improves **selected accuracy** over best single operator under equal compute.
4. Oracle improvement exists, but is secondary.
5. Selector achieves acceptable oracle capture: `>= 80%` for arithmetic/logic, audited threshold for legal/open-ended.
6. Result survives held-out tasks or held-out seed panels.
7. Cost-normalized lift is positive versus best temperature/nucleus baseline.

For publishable CDE:

- N-scaling advantage should appear across multiple N values, not only `N=10`.
- Domain routing should be demonstrated on real domain splits, not asserted.
- Selector calibration must be reported.
- The paper claim should be about **decorrelation converted into selected accuracy**, not just decorrelation observed.

**9. Priority Directive**

The single most important fix before implementation:

> Redefine the primary measurement and success gate around **candidate-set-level selected accuracy under equal compute, using deployable selectors only**, with oracle accuracy treated as a diagnostic ceiling.

Concretely: add `candidate_set_id` and `selection_trace`, implement operator-stratified consensus with abstention, separate oracle/evaluation from deployable selection, and make the first go/no-go criterion: “Does CDE select better answers than the best single operator at the same budget?”

Until that is fixed, the system can prove that diversity exists without proving that CDE is **Executive Verdict**

Yes, the CDE documents satisfy the *shape* of my directive. They correctly reframe Architecture 5 as a measurement-governed ensemble, and they identify the right three variables: candidate quality, error decorrelation, and selector reliability.

But they are not implementation-ready. The largest remaining flaw is that the documents still treat **oracle coverage and complementarity metrics as sufficient evidence**, when the real CDE claim must be:

> Under equal compute, a deployable selector chooses a better answer from a decorrelated operator mix than from the best single operator.

Right now, the design can still “win” on oracle/Jaccard and lose as a usable inference system.

**1. Does CDE Satisfy The Directive?**

Mostly yes.

It includes the required pieces: operator portfolio, diversity metrics, selector audit, N curves, equal-budget comparison, and relationship to the existing temperature experiment. That is the correct architectural direction.

What is still missing:

- A clean separation between **evaluation oracle** and **deployable selector**.
- A candidate-set-level schema. Selection happens over a set, but the trace schema is mostly per-candidate.
- A statistically valid validation plan. `25` arithmetic tasks is a pilot, not a decision-grade experiment.
- A primary endpoint based on **selected accuracy**, not oracle accuracy.
- A stronger equal-budget contract: equal `N`, equal generated-token budget, and equal wall-clock/cost-normalized comparisons.
- A real allocator protocol. The current greedy formula using `A * (1 - rho)` is a heuristic, not a defensible estimator of marginal coverage.
- A held-out split. The same traces are being used for characterization, operator choice, selector tuning, and success claims.

So: correct architecture, incomplete contract.

**2. Measurement Contract And Trace Schema**

The measurement contract is directionally good but incomplete.

Add these metrics:

- **Selected accuracy**: primary system metric.
- **Cost-normalized lift** over best single operator and best temperature/nucleus baseline.
- **Marginal unique solves** per operator: tasks solved by `O_b` that `O_a` misses.
- **Duplicate-basin rate / fingerprint collision rate**.
- **Answer-cluster diversity**: unique normalized answers, answer entropy, answer-cluster oracle.
- **Selector calibration**: precision, recall when oracle-positive, false-positive confidence, ECE/Brier if confidence is used.
- **Oracle-selector gap by N**.
- **Bootstrap or paired permutation CIs over tasks**, not only subset bootstraps over candidates.
- **Cluster-correctness association**: cluster purity or mutual information between trajectory cluster and correctness.
- **Extraction failure / ambiguity rate**: disagreement between answer-anywhere, last integer, final answer, and normalized extracted answer.

De-emphasize or demote:

- `answer_anywhere_correct` as a primary metric. It can over-credit outputs whose final answer is wrong.
- Raw `first_32_embedding` in JSONL as mandatory storage. Store a hash/path/reference or reduced vector; full embeddings can be artifact files.
- DBSCAN `eps=0.3` as a fixed truth. Treat clustering as an analysis method with sensitivity checks.
- Length heuristic as a selector. It is a weak prefilter, not a meaningful selector.

Trace schema is not sufficient yet. Add:

- `run_id`, `candidate_set_id`, `allocation_id`, `panel_id`, `candidate_index`.
- Model identity: checkpoint, quantization, tokenizer hash, chat template, git commit, library versions.
- Full generation config: max tokens, stop condition, top-k, top-p, temperature, repetition penalty, seed state.
- Full prompt/rendered input, not just task text.
- Output token IDs and final-answer extraction method/version.
- Operator artifact hashes: prefix tensor hash/norm/RMS, random token IDs, prompt template text/hash, position offset.
- Evaluator/verifier version and whether the verifier is deployable or oracle-only.
- A separate **selection trace**: selector id, scores/ranks for all candidates, selected trace id, confidence, fallback/abstention decision.

Selectors are set-level objects. They should not be embedded only as per-candidate fields.

**3. Decision Gates And Thresholds**

Several gates need correction.

Gate 1 currently says:

> IF max J < 0.8 for any pair: YES

That is logically wrong. It should be based on **minimum pairwise Jaccard**, not max.

Better gate:

- Candidate pair is complementary only if:
  - both operators are viable: `A >= floor`, `Y >= floor`;
  - `J(correct_sets) <= 0.7` or meaningful unique-solves count;
  - cross-operator error correlation is lower than within-operator correlation;
  - the pair improves oracle and selected accuracy under equal compute.

Threshold changes:

- `A > 0.2` is too absolute. Use relative viability too: operator accuracy should be at least `50-70%` of the best cheap operator unless it contributes unique solves.
- `Y > 0.7` is acceptable as a pilot cutoff, but core Tier 1 operators should probably target `Y > 0.85`.
- `rho < 0.3` is useful as a label, not a hard gate. With only 25 tasks, binary correlations are noisy. Require CIs or relative reduction versus within-operator correlation.
- `+2 tasks on 25` is acceptable as a pilot signal, not a validation claim. For validation, require a held-out larger set and paired uncertainty.
- `selector_accuracy > 60% of oracle` is too weak for arithmetic. For arithmetic/logic, target `>= 80%` of oracle. For legal/open-ended, require judge audit and calibration.

Most important gate change:

> CDE succeeds only if **selected accuracy** beats the best single-operator baseline under equal compute. Oracle improvement alone is not enough.

**4. Operator Portfolio Tiering**

Mostly correct, but change the tiers.

Move to Tier 1:

- **Random Token Prefix**. My prior directive explicitly required prefix vs temperature vs prompt paraphrase vs random-token prefix. It is a required control, not an extended operator.
- **Position Shift**, or at least a Tier 1 control. Zero soft prefix partially tests prefix-position effects, but pure position shift is the cleaner control.

Change treatment:

- **Zero Soft Prefix** is deterministic if decoding is greedy. Do not generate `N=10` identical zero-prefix candidates. Treat it as a control, not a sampled operator.
- **Prompt Rephrase** uses templates, not seeds. Model it as `template_id`, not stochastic seed.
- **Neuro-symbolic** should be in a tool/verifier-augmented track. It is valuable, but it is not a fair black-box candidate generator unless clearly budgeted and domain-scoped.
- **ALM** should be split:
  - basin/cluster measurement belongs in Phase 1 analysis;
  - ALM-guided generation can be Tier 2 after basin stability is proven.
- **CIR, Attention Surgery, GGIO** are correctly Tier 3.

**5. Selector Protocol**

Partly sound, but the missing selector is critical:

> **Operator-stratified answer consensus with abstention.**

Raw majority vote is wrong for CDE because it is biased by allocation. If you sample 6 prefix and 4 rephrase candidates, majority vote mostly measures sampling ratio. The selector should score normalized answer clusters by:

- number of distinct operators supporting the answer;
- per-operator quality prior;
- independence/decorrelation prior;
- within-answer confidence;
- verifier result if available;
- fallback/abstention if no cluster is credible.

Order changes:

For arithmetic/logic/code:

1. Degenerate filter.
2. Normalize/extract candidate answers.
3. Deployable formal verifier if available.
4. Operator-stratified answer-cluster consensus.
5. Self-certainty as tiebreaker, not primary selector.
6. Fallback to greedy/baseline or abstain if confidence is low.

For legal/open-ended:

1. Degenerate filter.
2. Constraint/rubric extraction.
3. LLM judge or pairwise judge over candidates.
4. Cross-operator agreement and confidence calibration.
5. Abstention/fallback path.

Also: exact match against ground truth is not a deployable selector. It is evaluation oracle machinery.

**6. N-Scaling Curves And Subsampling**

Subsampling from `N=10` is valid only for a narrow claim:

> It estimates expected oracle/selected accuracy for subsets of an already generated finite candidate pool, for `N <= 10`.

It is not valid for true `N=16` scaling.

Risks:

- You cannot infer `N=16` from `N=10`; “use all 10 and bootstrap” is invalid for additional unique candidates.
- Candidate subsets are correlated, so CIs will be too optimistic if task-level uncertainty is ignored.
- The `25` task set dominates uncertainty.
- If the same data chooses the operator and estimates the curve, curves are selection-biased.
- Selector behavior changes with N, especially majority vote.
- Finite seed pools can make curves look saturated or unusually strong by accident.

Fix:

- Generate at least `N=16`, preferably `N=30`, for Tier 1 operators if N-scaling is part of the claim.
- Bootstrap over tasks as the primary uncertainty unit.
- Use held-out seed panels for confirmation.
- For top ensembles, generate actual ensemble allocations at target N, not just post-hoc mixtures unless allocation was pre-registered.

**7. Relationship To Temperature Comparison**

The relationship makes sense.

The temperature comparison design should become CDE Experiment 0, not a separate line of work. But it must be upgraded with:

- trace schema;
- random-token prefix Tier 1 control;
- first-32-token fingerprints;
- pairwise error correlation;
- correct-set Jaccard;
- selector audit;
- selected accuracy;
- equal compute and equal token accounting.

Without those additions, it remains only a baseline comparison, not CDE evidence.

**8. Success Criteria**

Section 10 is too oracle-heavy and too weak statistically.

Replace Minimum Viable CDE with:

1. Complete trace and selection records for all Tier 1 operators.
2. At least two viable operators with measurable unique-solves or lower cross-error correlation.
3. Best 2-operator ensemble improves **selected accuracy** over best single operator under equal compute.
4. Oracle improvement exists, but is secondary.
5. Selector achieves acceptable oracle capture: `>= 80%` for arithmetic/logic, audited threshold for legal/open-ended.
6. Result survives held-out tasks or held-out seed panels.
7. Cost-normalized lift is positive versus best temperature/nucleus baseline.

For publishable CDE:

- N-scaling advantage should appear across multiple N values, not only `N=10`.
- Domain routing should be demonstrated on real domain splits, not asserted.
- Selector calibration must be reported.
- The paper claim should be about **decorrelation converted into selected accuracy**, not just decorrelation observed.

**9. Priority Directive**

The single most important fix before implementation:

> Redefine the primary measurement and success gate around **candidate-set-level selected accuracy under equal compute, using deployable selectors only**, with oracle accuracy treated as a diagnostic ceiling.

Concretely: add `candidate_set_id` and `selection_trace`, implement operator-stratified consensus with abstention, separate oracle/evaluation from deployable selection, and make the first go/no-go criterion: “Does CDE select better answers than the best single operator at the same budget?”

Until that is fixed, the system can prove that diversity exists without proving that CDE is useful.
