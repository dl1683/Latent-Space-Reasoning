## The Core Thesis

**Improvement from inference-time resampling is bounded by THREE factors:**
1. **Candidate quality**: mean accuracy of individual candidates
2. **Error decorrelation**: whether candidates fail on DIFFERENT tasks (low pairwise error correlation)
3. **Selector reliability**: whether the selector can identify the correct candidate when it exists

**Current approach** (random prefix perturbation + exact-match oracle) operates blind on all three:
- Quality: unknown relationship between perturbation magnitude and individual accuracy
- Decorrelation: never measured, only oracle coverage observed
- Selector: extract_answer + exact match is brittle; for open-ended tasks, LLM judge is unvalidated

**CDE makes all three explicit, measurable, and optimizable.**

## Phase 1: The Operator Registry

An "operator" is any inference-time intervention that produces a candidate output different from the greedy baseline. The CDE framework treats operators as interchangeable diversity generators with measurable properties.

| O9 | Attention bias | Attention | head_ids, positions, bias | Yes (head selection) |

### Operator Properties (Measured, Not Assumed)

For each operator O, we measure on a calibration set (25 arithmetic tasks):

**P1: Individual accuracy (quality)**
- A(O) = mean accuracy of candidates generated by operator O
- Higher = better candidates on average

**P2: Oracle accuracy (coverage)**  
- oracle(O, N) = fraction of tasks where at least 1 of N candidates is correct
- Higher = more problems solvable in principle

**P3: Pairwise error correlation (decorrelation)**
- For operator O with seeds i,j: corr(O,i,j) = Pearson correlation between binary error vectors
- Mean over all seed pairs: rho(O) = mean(corr(O,i,j))
- Lower rho = more decorrelated = more diverse exploration

**P4: Trajectory diversity (class count)**
- Cluster first-32-token embeddings of N candidates into K classes
- K(O, N) = number of distinct trajectory classes
- Higher K = more diverse exploration

**P5: Correct-set Jaccard (complementarity)**
- For operators O_a, O_b: J(O_a, O_b) = |correct(O_a) ∩ correct(O_b)| / |correct(O_a) ∪ correct(O_b)|
- Low Jaccard between operators = they solve DIFFERENT problems
- High Jaccard = redundant

**P6: Effective candidate yield**
- Y(O, N) = fraction of N candidates that are non-truncated, non-degenerate
- If Y < 0.5, most of the compute budget is wasted

**P7: Compute cost**
- C(O) = wall-clock time per candidate relative to greedy baseline
- Temperature = 1.0x (same speed), activation steering ~1.1x (hook overhead), gradient optimization ~20x

### Why These Properties Matter

The theoretical oracle accuracy under best-of-N with M operators is:
```
oracle_M_N ≈ 1 - ∏_m (1 - A(O_m))^N   [if fully decorrelated]
oracle_M_N ≈ 1 - (1 - max_m A(O_m))^(M*N)  [if fully correlated]
```

The gap between these bounds = the value of decorrelation. If operators are fully correlated, using M operators gives the same benefit as 1 operator with M*N samples. Only decorrelation provides super-linear benefit.

## Phase 2: The Measurement Contract

### What MUST Be Measured Before Any Architecture Decision

This is the critical gap Codex identified: we've been designing architectures without knowing whether the operators we have actually decorrelate.

### Experiment 0: Operator Characterization Matrix

**For each operator O in {O1, O3, O4, O5}:**
(O1=prefix, O3=temperature, O4=nucleus, O5=prompt rephrase)

1. Generate N=10 candidates per operator per task (25 tasks)
2. Compute: A(O), oracle(O,10), rho(O), K(O,10), Y(O,10), C(O)
3. Compute pairwise: J(O_a, O_b) for all operator pairs

**Expected data volume:**
- 4 operators × 10 seeds × 25 tasks = 1000 generations
- For temperature/nucleus: 3 replicate panels × 10 seeds × 25 tasks = 750 additional
- Total: ~1750 generations (~3-4 hours GPU)

### Pre-Registered Interpretation Criteria

**Decorrelation threshold**: rho(O) < 0.3 = "meaningfully decorrelated"
- If ALL operators have rho > 0.5, single-operator best-of-N is sufficient. Multi-operator adds no value.

**Complementarity threshold**: J(O_a, O_b) < 0.7 = "complementary operators"
- If all operator pairs have J > 0.8, they solve the same problems. Multi-operator is redundant.

**Quality threshold**: A(O) > 0.2 = "viable operator"
- Operators with A < 0.1 produce mostly garbage candidates. Not useful regardless of diversity.

**Yield threshold**: Y(O) > 0.7 = "efficient operator"
- If more than 30% of candidates are degenerate, the operator wastes budget.

### Experiment 1: Cross-Operator Ensemble

**After Experiment 0 identifies which operators are complementary:**

1. For each complementary pair (O_a, O_b):
   - Generate N/2 candidates with O_a, N/2 with O_b (total N=10)
   - Compute oracle accuracy
   - Compare with: N=10 all from O_a, N=10 all from O_b
2. For the best triple:
   - Generate N/3 from each of 3 operators (total N~10)
   - Compare with best single-operator N=10

**Pre-registered success criterion:**
- Ensemble oracle ≥ best single-operator oracle + 2 tasks (≥8pp improvement)
- AND: ensemble uses the same total compute budget (N=10 total candidates)

If the ensemble doesn't beat the best single operator under equal compute, the multi-operator approach adds complexity without benefit.

### Experiment 2: Selector Audit

**The verifier ceiling is the most underappreciated constraint.**

For each selector S:
1. **S1: extract_answer + exact match** (current, for arithmetic)
2. **S2: self-certainty** (mean log-prob of generated tokens)
3. **S3: answer-length heuristic** (prefer medium-length answers)
4. **S4: majority vote** (most common answer among N candidates)
5. **S5: LLM judge** (Claude or local model evaluates quality)

For each selector on the N=10 candidate sets:
- Selector accuracy = fraction of tasks where the selector picks a correct candidate (when one exists in the set)
- False positive rate = fraction of tasks where the selector picks an incorrect candidate confidently
- Comparison: selector accuracy vs oracle accuracy (the gap = selector inefficiency)

**Pre-registered interpretation:**
- If selector accuracy < 0.5 * oracle accuracy, the selector is the bottleneck. Improving candidates is useless until the selector improves.
- If selector accuracy > 0.8 * oracle accuracy, the selector is adequate. Focus on candidate diversity.

### Component 2: Candidate Generator

Generates candidates from the selected operator ensemble:
```python
class CandidateGenerator:
    def generate(self, question: str, operator_alloc: List[(str, int)]) -> List[Candidate]:
        candidates = []
        for op_name, n in operator_alloc:
            operator = self.pool.operators[op_name]
            for seed in range(n):
                output = operator.generate(question, seed=seed)
                candidates.append(Candidate(
                    text=output,
                    operator=op_name,
                    seed=seed,
                    metadata=operator.get_metadata(output)  # logprobs, certainty, etc.
                ))
        return candidates
```

### Component 3: Selector Stack

A pipeline of selectors, from cheapest to most expensive:
```python
class SelectorStack:
    """
    Multi-stage selector: cheap filters first, expensive judge last.
    """
    stages: List[Selector] = [
        DegenerateFilter(),      # Remove truncated, repetitive, empty
        FormatFilter(),          # Remove outputs that don't contain an answer
        MajorityVoteRanker(),    # Rank by answer frequency
        SelfCertaintyRanker(),   # Rank by model confidence
        # OracleJudge() — only for evaluation, not deployment
    ]
    
    def select(self, candidates: List[Candidate]) -> Candidate:
        remaining = candidates
        for stage in self.stages:
            remaining = stage.filter_or_rank(remaining)
            if len(remaining) == 1:
                return remaining[0]
        return remaining[0]  # top-ranked by final stage
```

### Component 4: Measurement Engine

Computes all properties (P1-P7) for operator characterization:
```python
class MeasurementEngine:
    def characterize_operator(self, operator: Operator, tasks: List[Task], N: int) -> OperatorProperties:
        results = []
        for task in tasks:
            for seed in range(N):
                output = operator.generate(task.question, seed=seed)
                results.append({
                    'task_id': task.id,
                    'seed': seed,
                    'output': output,
                    'correct': task.evaluate(output),
                    'embedding': self.embed_first_32(output),
                    'length': len(output),
                    'truncated': len(output) >= max_tokens,
                })
        
        return OperatorProperties(
            accuracy=mean([r['correct'] for r in results]),
            oracle=mean_over_tasks(any_correct_per_task(results)),
            error_correlation=compute_pairwise_correlation(results),
            trajectory_classes=cluster_embeddings(results),
            yield_rate=1 - mean([r['truncated'] for r in results]),
            # etc.
        )
    
    def compute_complementarity(self, op_a_results, op_b_results) -> float:
        correct_a = set(t for t in tasks if any_correct(op_a_results, t))
        correct_b = set(t for t in tasks if any_correct(op_b_results, t))
        return jaccard(correct_a, correct_b)
```

### Component 5: Budget Allocator

Given total compute budget B (in forward passes), optimally allocates across operators:
```python
class BudgetAllocator:
    def allocate(self, budget: int, operator_properties: Dict[str, OperatorProperties]) -> Dict[str, int]:
        """
        Optimization: maximize expected oracle accuracy under budget constraint.
        
        Simple greedy approach:
        1. Start with 0 candidates per operator
        2. Add 1 candidate to the operator that maximally increases expected oracle
        3. Repeat until budget exhausted
        
        Expected oracle increase from adding candidate to operator O:
        ΔE[oracle] ≈ (1 - current_coverage) × A(O) × (1 - rho(O))
        
        The (1-rho) term captures: decorrelated operators contribute more per candidate.
        """
        allocation = {op: 0 for op in operator_properties}
        coverage = 0.0
        
        for _ in range(budget):
            best_op = max(operator_properties.keys(), 
                         key=lambda op: self.marginal_oracle_gain(op, allocation, operator_properties))
            allocation[best_op] += 1
        
        return allocation
```

## Phase 5: Failure Analysis

### Failure Mode 1: All Operators Are Correlated
**What**: rho(O_a, O_b) > 0.7 for all operator pairs
**When**: The model has a strong default attractor that no intervention can escape
**Impact**: Multi-operator ensemble = single operator. CDE degenerates to simple best-of-N.
**Detection**: Experiment 0 measures this directly
**Mitigation**: None. If correlations are inherently high, the entire CDE approach provides no benefit over simple temperature sampling with higher N.

### Failure Mode 2: Selector Bottleneck
**What**: Selector accuracy < 50% of oracle accuracy
**When**: The selector can't reliably identify correct candidates
**Impact**: Even perfect diversity doesn't help — the selector picks wrong candidates
**Detection**: Experiment 2 measures this directly
**Mitigation**: Invest in better selectors (Pillar 2) before investing in better diversity (Pillar 1)

### Failure Mode 3: Quality-Diversity Tradeoff
**What**: High-diversity operators (high K, low rho) have low quality (low A)
**When**: Interventions that create diverse trajectories also degrade reasoning
**Impact**: The budget allocation faces a Pareto frontier: can't get both quality and diversity
**Detection**: Plot A(O) vs rho(O) for all operators. If negatively correlated, the tradeoff is real.
**Mitigation**: This is EXPECTED for temperature (higher T = more diverse but lower quality). The question is whether prefix perturbation breaks this tradeoff (moderate diversity + preserved quality).

### Failure Mode 4: Domain Transfer Failure
**What**: Calibration on arithmetic doesn't transfer to legal/planning
**When**: Different task types have fundamentally different attractor landscapes
**Impact**: Must recalibrate per domain. CDE loses the "general-purpose" claim.
**Detection**: Run Experiment 0 on legal tasks and compare operator properties
**Mitigation**: Domain-specific configurations are acceptable if the FRAMEWORK transfers even when the specific allocation doesn't.

### Failure Mode 5: Compute Budget Dominates
**What**: Simple temperature N=50 beats optimized CDE N=10
**When**: The selector improvement from CDE doesn't compensate for the raw coverage of more candidates
**Impact**: CDE is a complexity tax with no return
**Detection**: Oracle curves: plot oracle accuracy vs N for each operator. If any single operator's curve dominates the CDE curve at the same total cost, CDE loses.
**Mitigation**: CDE should be compared at EQUAL COMPUTE, not equal N. If prefix costs 1x and gradient optimization costs 20x, a single gradient-optimized candidate costs the same as 20 random prefix candidates.

## Phase 6: The Theoretical Foundation

### Ensemble Theory Formalization (from cross-domain research)

For a best-of-N system with K operators, each producing N_k candidates:
- Total candidates: N = sum(N_k)
- Individual accuracy for operator k: a_k = P(candidate from O_k is correct)
- Error correlation between operators i,j: rho_{ij}

**Expected oracle accuracy:**
```
P(oracle correct) = 1 - P(all candidates wrong)
                  = 1 - ∏_k P(all N_k candidates from O_k wrong | other operators' candidates wrong)
```

If operators are independent (rho=0):
```
P(oracle) = 1 - ∏_k (1 - a_k)^{N_k}
```

If operators are perfectly correlated (rho=1):
```
P(oracle) = 1 - (1 - max_k a_k)^1  =  max_k a_k
```
(i.e., oracle = best single candidate, no matter how many you generate)

**The partial-correlation case** (0 < rho < 1) requires the multivariate normal CDF or copula model. For binary outcomes, the beta-binomial model is appropriate:
```
P(all N from O_k wrong) = beta_binomial_cdf(0; N_k, alpha_k, beta_k)
```
where alpha_k, beta_k are derived from a_k and rho_k.

**Key insight**: The marginal value of one additional candidate from operator O_k is:
```
ΔP(oracle) ≈ (1 - P(oracle currently)) × a_k × (1 - rho_k)
```

This is the **decorrelation dividend**: each additional candidate's value is scaled by (1 - rho). Highly correlated operators get diminishing returns fast; decorrelated operators maintain value longer.

### The Selector Ceiling

From "The Limits of Inference Scaling Through Resampling":
With an imperfect selector of accuracy s (probability of correctly choosing the right candidate):
```
P(selected = correct) ≤ s × P(oracle correct) + (1-s) × a_mean
```

As N → ∞, P(oracle) → 1 (for any a > 0), but P(selected) is bounded by s.

**Implication**: Beyond N ≈ -log(1-s) / log(1-a), adding more candidates has negligible returns. The selector is the ceiling.

For our system: if s=0.8 (selector picks correctly 80% of the time when a correct candidate exists) and a=0.3 (30% individual accuracy), the ceiling is around N=8. Beyond 8 candidates, investment should go into the selector, not more candidates.

### Optimal Budget Allocation (Formal)

Given:
- Budget B (total forward passes)
- K operators with properties (a_k, rho_k, c_k) where c_k = cost per candidate
- Selector accuracy s

Maximize:
```
E[correct] = s × P(oracle | allocation) + (1-s) × weighted_mean(a_k, allocation)
```

Subject to:
```
sum(N_k × c_k) ≤ B
```

This is a constrained optimization solvable by dynamic programming (discrete N_k) or Lagrange multipliers (continuous relaxation).

## Phase 7: What This Design Document Intentionally Excludes

### Excluded: Iterative Refinement
CDE is a single-generation-plus-selection framework. Architectures 12 (IDR) and 17 (TER) add iterative refinement as an orthogonal improvement. CDE should be established first; refinement can be layered on top.

### Excluded: External Models
Architecture 4 (Inverse Speculative) uses an external oracle. CDE uses only the target model plus lightweight selectors. External-model architectures are a separate tier.

### Excluded: Causal Analysis
Architecture 11 (CIR) provides mechanistic understanding. CDE is agnostic to mechanism — it works regardless of WHY operators decorrelate. Causal analysis is complementary but not required.

### Excluded: Continuous Reasoning
Architecture 6 (Token-Free) operates in a fundamentally different paradigm. CDE treats the model as a generation black box. Continuous reasoning modifies the model's internal loop. Not compatible in the same framework.

## Phase 9: Predictions (Pre-Registered)

### P1: Prefix perturbation and temperature sampling solve DIFFERENT tasks
- Jaccard(prefix_correct, temp_correct) < 0.7
- Rationale: prefix perturbs the embedding space (continuous, OOD); temperature perturbs the sampling distribution (discrete, in-distribution). Different mechanisms → different failure modes → different correct sets.
- If WRONG: prefix is just a more complex temperature. Framework still useful but prefix has no unique value.

### P2: Multi-operator ensemble beats best single operator at equal N
- oracle(prefix_5 + temp_5, N=10) > max(oracle(prefix, N=10), oracle(temp, N=10))
- By at least 2 tasks (8pp)
- If WRONG: operators are redundant. CDE reduces to "just use the best single operator."

### P3: Error correlation within-operator > between-operator
- rho(prefix_i, prefix_j) > rho(prefix_i, temp_j) for most i,j
- Rationale: same-type perturbations produce more similar outputs than cross-type perturbations
- If WRONG: the operator type doesn't matter, only the random seed. Simplify to just temperature sampling.

### P4: Selector accuracy is the binding constraint at N=10
- For N=10, selector accuracy < 0.8 × oracle accuracy
- Rationale: with 10 candidates, the oracle is strong (80-100%), but the selector struggles to distinguish correct from plausible-but-wrong candidates
- If WRONG: selector is good. Focus entirely on diversity/coverage.

### P5: Prefix perturbation has higher quality AND lower diversity than temperature
- A(prefix) > A(temp_0.6) AND K(prefix) < K(temp_0.6)
- Rationale: greedy decoding with soft prefix produces more coherent (higher quality) but less diverse outputs than stochastic temperature sampling
- If WRONG: prefix is strictly dominated by temperature. Abandon prefix in favor of temperature.
